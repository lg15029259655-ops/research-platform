# 第二个站点上线前复盘（2026-10-09）

历史目标：曾计划将 `lunyu-lab.site` 作为少量用户测试站点，部署在校园雷达现有主机上。**实际后来改为阿里云香港 ECS 独立部署，已上线**；下文的同机部署与备案安排仅是历史方案。下面区分**历史确实发生的故障**与**当时提前查到的风险**，避免把推测写成事故。

## 上次校园雷达部署的真实故障

| 证据 | 当时的问题 | 这次的硬性检查 |
| --- | --- | --- |
| 提交 `4203793` | GitHub Actions 直接写入多行 SSH 私钥，编码/换行处理出错，后改为 base64 解码并用 `ssh-keygen -y` 验证。 | 发布前验证所用 SSH 凭据能登录；若使用 Actions，文档与 workflow 的 Secret 名称必须完全一致。不要把私钥或 token 写入仓库、日志。 |
| 提交 `54a2d41` | 发布用户不能写 `/opt/campus-radar` 的发布根目录。 | 单独确认新发布用户对 `/opt/research-platform/releases` 有写权限，运行用户对 `current` 有读权限。不要修改旧站点权限。 |

另一个已发现的文档漂移：校园雷达 `DEPLOYMENT.md` 写的是 `SERVER_SSH_KEY`，现有 workflow 实际读取 `SERVER_SSH_KEY_B64`。新项目目前没有 GitHub 发布流水线；建立时要把凭据名称写成单一来源，并在第一次运行前检查。

## 本次提前发现并已修复

- 首页健康检查和 PDF 组件原来直接访问 `http://127.0.0.1:8000`。发布后这会指向访客自己的电脑。现已统一读取 `frontend/src/lib/api.ts` 中的 API 地址；生产构建设置 `NEXT_PUBLIC_API_URL=''`，请求走本域名 `/api`。
- 首页写着“本地运行”“本地服务已连接”，不适合公开网页；已改为服务状态描述。
- 部署模板把新站点隔离到 `3100/8100`、`/opt/research-platform`、`/var/lib/research-platform` 和独立 Nginx 域名；不覆盖校园雷达配置。

## 四道上线关口

1. **域名与主机**：域名审核、实名及新网站 ICP 备案完成；确认 DNS 指向当前主机；记录校园雷达现有 Nginx、systemd 和数据备份状态。若域名未满足条件，只做本机或受限预演，不公开启用新域名。
2. **构建与权限**：在 Linux 构建 Next standalone，检查 `server.js` 和 `.next/static`；创建独立用户及 Python venv；确认生产 env 不进入仓库且权限为 `600`；运行 `python3 deploy/preflight.py --server`，所有 FAIL 清零。发布包必须排除 `.env`、本地 SQLite、上传文件和 `node_modules`。
3. **先本机后代理**：先直接检查 `127.0.0.1:8100/api/health` 和 `127.0.0.1:3100`；再安装新域名 Nginx 配置，`nginx -t` 通过后重载。签证书后核对 HTTP 跳 HTTPS，以及 `/api`、PDF 文件、Cookie、流式响应；从外部浏览器实际访问一次。不要在新站点发布脚本中删除或替换旧站点的 Nginx 文件。
4. **运行验收与回退**：记录启动前后内存、磁盘、两个站点的健康状态；用 2–3 名用户并发测试检索、PDF 上传/打开、AI 精读与综合；确认数据库/PDF 备份和一次恢复。发布前保留旧版本与数据库快照；出现 502、OOM、登录态丢失或旧站异常，立即回退新站点发布链接并检查日志。

**当前未完成的验收**：2026-10-09 新截图显示域名命名状态“正常”，但尚无实名认证和新网站 ICP 备案完成的证据；还没有本项目的 Git 仓库/发布流水线，也没有在目标 Linux 主机做构建、资源测量、证书、Nginx 与端到端验收。因此不能把本地构建成功等同于已可公开上线，更不能保证一次发布绝对零故障。
